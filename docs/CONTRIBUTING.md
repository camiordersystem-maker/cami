# 開発フロー・コミット規約

このリポジトリで変更を加えるときの共通ルール。人間の開発者・AIエージェント（Claude Code / Codex / Manus AI等）共通で従う。

## ブランチ運用

```
staging (ステージング) ──確認OK──▶ main (本番)
```

- **`main`** = 本番。Vercel（`cami2026`プロジェクト）の Production 環境が自動デプロイされる。
- **`staging`** = ステージング。Vercel Preview 環境（`staging`ブランチにスコープした環境変数、独立したNeon DB）が自動デプロイされる。詳細は [STAGING.md](STAGING.md)。

**手順:**

1. 修正・機能追加は `staging` に直接コミット（または `staging` から切った作業ブランチで作業し、`staging` へマージ）。
2. push → Vercel Previewが自動ビルド。ステージングURLで動作確認。
3. 問題なければ `staging` → `main` へ Pull Request を作成してマージ。マージ後、Vercel Productionが自動デプロイされる。

**やってはいけないこと:**

- `main` に直接コミット・pushしない（ステージングで確認していない変更が本番にそのまま出てしまう）。
- `staging` を作業のたびに作り直したり削除したりしない。`main`と同様、常に存在し続ける前提のブランチ。

## コミットメッセージの書き方

このリポジトリの実際の履歴で使われている形式:

```
<type>: <日本語での要約>
```

`git log --oneline` で実例が確認できる。よく使われる `type`:

| type | 意味 | 例 |
|---|---|---|
| `feat` | 新機能追加 | `feat: 監査ログ閲覧画面を追加（スーパー管理者限定）` |
| `fix` | 不具合修正 | `fix: F-03再回帰の真因を修正 — セッション読込中はviewer扱いにする(fail-closed)` |
| `security` | セキュリティ対応 | `security: 依存脆弱性の解消・セキュリティヘッダー追加・セッション有効期限短縮` |
| `docs` | ドキュメントのみの変更 | `docs: cami2026プロジェクトの既存Vercel環境変数を棚卸しして記録` |
| `chore` | 上記に当てはまらない雑務（依存更新等） | `chore: upgrade next and clear audit findings` |

**要約の書き方:**
- 「何をしたか」より「なぜ・何が変わったか」が分かるように。単に `fix: バグ修正` のような曖昧な要約は避ける。
- 外部からの指摘（Manus AIのテスト報告など）を修正した場合は、その出どころを要約に含める（例: `fix: Manus AIのテスト報告で発見した注文作成500エラーを修正`）。これにより、後から「なぜこの修正が入ったか」を追跡できる。
- 1コミット1目的が基本。無関係な変更を1つのコミットに混ぜない。

## Pull Requestの書き方（`staging` → `main`）

`.github/pull_request_template.md` が自動で挿入される。埋める項目:

- **変更内容**: 何を変えたか（コミットメッセージの要約でよい）
- **確認方法**: ステージングURLでどう確認したか（画面・操作手順・結果）
- **影響範囲**: 注文・請求書・在庫など、お金や在庫が絡む処理に触れた場合は明記する
- **ロールバック**: 問題が起きた場合に戻せるか（DBマイグレーションを含む変更は特に）

## 環境変数・DBマイグレーションを伴う変更の注意

- `vercel-build` スクリプトは、ビルドのたびに `src/lib/db/migrate.pg.ts` を実行しDBマイグレーションを自動適用する。新しいマイグレーションSQLファイルを追加した場合は `src/lib/db/migrate.pg.ts` の `EXTRA_MIGRATIONS` 配列にファイル名を追記すること（追記を忘れると、そのファイルは永久に適用されない）。
- Cloudflare Workers対応後は `src/lib/db/index.ts` のDB接続がリクエスト単位のスコープになっている（`RUNTIME_TARGET=cloudflare-workers`時）。`db`を直接importして使う分には意識不要だが、DB接続のライフサイクル自体を変更する場合は、Cloudflare Workersの「リクエストをまたいだI/O使い回し禁止」制約を必ず踏まえること。
